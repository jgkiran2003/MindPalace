MindPalace — architecture and code flow

A local-first personal knowledge system: a Markdown vault is indexed into LanceDB, structured “claims” live in SQLite, and local Ollama models do embeddings, extraction and conversation. The only front end today is the palace CLI.

1 · Components and layers

Each front-end command lands on one orchestrator; orchestrators share two stores and two external services. chat composes the searcher and the claim pipeline rather than owning its own storage.

3 · palace index — vault to searchable chunks

Re-indexing is replace-by-file: a document's old chunks are deleted before its new ones are written.

4 · palace search — three-leg hybrid retrieval

The same HybridSearcher.retrieve serves both search and every chat turn. Tags on the left refer to sections of the master specification.

5 · palace chat — one conversational turn

Claim extraction runs as a background task so it never delays the reply. A lock serializes claim tasks. Greetings skip extraction. Each finished task ends in one outcome (saved, no claims, malformed output, model/embedding failure, storage failure) and prints a [claims] line; nothing is written unless extraction succeeded.

6 · Claims — manual commands and the resolution rules

Both claim add and the chat pipeline end in propose_claim, which decides whether a new claim replaces, coexists with, or conflicts with what is already stored for the same entity:attribute key.

7 · palace compile — raw notes to an indexed compiled note

The order is chosen so every failure is recoverable: nothing about the sources changes until the compiled note is safely indexed.

8 · Deferred items and caveats

  • Archival is vault-driven. ChunkStatus has only raw and compiled and the model files are protected, so an archived raw note keeps status: raw, gains processed: true, and is simply not indexed. Delete the two marker lines and re-index to restore it.
  • Compiled chunks do not carry derived_from_chunk_id. The field holds one id and a compiled note has many sources; provenance lives in the note's derived_from / derived_from_paths frontmatter.
  • Deferred (spec Phase 4): capture.py / normalizer.py (raw staging, voice-audio retention), and deriving claims from compiled notes.
  • Claims search is vector-only. search_claims accepts query_text but ignores it, so the claims leg is not the vector+text fusion described in spec §3.1.
  • Claim writes are per-claim transactions. If claim k of a batch fails, earlier ones stay committed; the failure report lists them.
  • Chat history is in-memory and unbounded; very long sessions will exceed the model's context window.
  • Production extraction prompt differs from the benchmark winner in scripts/eval_extractor.py; accuracy work is deliberately deferred.
  • SQLite is reopened per call in _ReopeningClaimsStoreAdapter, because retrieval and claim tasks run in worker threads.
